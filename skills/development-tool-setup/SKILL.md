# Development Tool Setup

Resolve the missing capability, selected tool, target machine, current installation/invocation mode and authorization. Keep credentials, browser profiles/workspaces and dependencies separate per machine.

- Choose from available capabilities first, inspect schemas/help and actual support. Match format/coverage/state/platform/account/cost/data boundaries. Browser interaction differs from tracing, symbol retrieval from text search, proofreading from translation.
- Choose CLI/Skill/MCP from actual integration, shell access, repeatability/artifacts and data/account scope. CLI may return JSON or keep sessions, so state alone does not require MCP. Verify original errors/output/exit codes, a config entry does not prove tool availability.
- Install/update/remove only the selected tool. Purpose profiles filter a menu, not authorize a package group. Preserve compatible providers, runtime/project versions, roots/accounts, dictionaries and built-in/plugin-managed packages.
- Source changes do not authorize unrelated local installs, remote publication or provider replacement. Never store credential values in code/docs/reports.

For checkout/wheel/wizard installation, Python bootstrap, updates or purpose/language-specific recipes, read [maintained setup](references/maintained-setup.md). It preserves exact entry points, flags, conflict/backup handling and source-doc routing.

After selecting an integration, read only its relevant sections in [integration verification](references/integration-verification.md), including lifecycle cleanup when diagnosing stuck servers/viewers. Preserve tool-specific boundaries and separate registration/package checks, authentication, client discovery and actual use.

If setup is unavailable, diagnose through installed tools/current official documentation and identify the required approved location or one reviewed installation. Do not guess personal paths/endpoints or install all tools. Report actual changes/backups/checks and concrete remaining prerequisites.
