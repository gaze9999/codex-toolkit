# Public and private delivery

Read when arranging development sources, instructions or delivery for public, private or mixed audiences. Use the methods relevant to the requested outcome; this is not a mandatory audit for ordinary implementation.

## Resolve current access and intended delivery

Confirm the actual working directory, Git root, remote, branch, tracked state and applicable instructions for the affected sources. Resolve current visibility separately from the user's intended public scope. Private development followed by a public formal version is public-target delivery from the planning stage; the public source, history and artifacts still need review before release. Current private access does not authorize publication.

For work that stays private, retain the approved environment and intended readers. For a public target, identify what will be published: selected code or data, a repository with history, a package, a website, or documentation. For mixed delivery, distinguish the public output from the private material that supports it. Leave an undecided public scope explicit while continuing independent private work.

## Choose a source arrangement

Use the simplest arrangement that preserves ownership and the intended boundary. Separate Git roots can keep private design and tooling apart from public code. An existing private repository may instead produce reviewed exports or a public release source. A shared root needs explicit tracked-file and artifact boundaries. Choose from actual consumers and release policy; do not mandate a second repository or move unrelated work.

Keep personal agent instructions, private design, diagnostic material and development-only assets outside the selected public scope when they are not part of the product. Check tracked state before relying on ignore rules. When converting a private repository to public, review the history that will become reachable, not only its latest tree. Repository visibility changes and history rewrites require their own authorization.

For reusable UI or other libraries, keep shared behavior with its maintained owner and business fields/rules with the consumer. Local adjacent-source access can aid development; record relevant commits and actual asset digests when it affects delivery identity. Keep uncommitted inputs distinct from a packaged release. Select loader, module, style or browser checks only for the affected integration; retain unavailable device/platform checks as pending.

## Choose data and update methods

When private structured sources produce public content, derive an explicit output schema or field allowlist from what the public consumer actually uses. Private reasons, drafts and validation notes can stay in the source owner. Inspect generated output and build inputs for unintended private dependencies. Published browser data remains readable even when its authoring source is omitted from a build.

When maintaining content or configuration, distinguish the source, generated candidate, application and publication. Select validation from the actual schema and consumers: stable identity, localized copy, units/ranges, relationships or cycles may matter. Use candidate digests, revision-conflict checks, recoverable backups and atomic replacement when needed for reproducible or concurrent writes. Changes to persisted content need the relevant compatibility check. Authoring tools follow the approved schema and rules; new identities or behavior require the corresponding source decision.

Use an available packaging-acceptance workflow for artifact/source evidence and actual platform checks. Avoid adding a new CLI, database or GUI just to express the method.

## Choose inspection depth and document readers

Tie public-scope checks to what will be exposed and to the request. A selected artifact check may inspect only mapped files. Publishing a previously private Git history, suspected exposure or an explicitly requested history audit may require reachable refs, commits, blobs and renamed paths. Compare remote refs when remote state is part of the claim. State inspected scope separately from old clones, caches or unreachable objects that were not inspected. Redact findings and never print credential values. For cleanup methods and mutation authorization, read [sensitive-data removal](sensitive-data-removal.md).

Write for the intended reader. A product or player README can emphasize purpose and first use; contributor documentation can hold architecture, framework/build details and engineering evidence. Keep information that affects use, compatibility or licensing visible to its reader. Select an available readme-maintainer workflow for presentation; do not make one outline compulsory or copy a private design into public documentation.

## Acceptance and authorization

Review the selected public candidate and affected private sources against their actual boundary. Keep source identity, local validation, installation, runtime use, remote publication and remaining acceptance separate. Preserve concurrent changes and the existing index. Publication, history cleanup, Git operations, visibility changes, deployment and external data transfer remain individually authorized actions.
