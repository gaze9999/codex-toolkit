# Shared project and device workflow

Read when the user requests persistent project tracking, cross-device configuration or recurring document maintenance. Reuse the selected task/document platform and existing installation writers; this reference adds no scheduler or account access.

## Keep a single owner

| Material | Canonical owner |
|---|---|
| Portable public tools, Skills and generated Plugins | Public toolkit |
| Personal choices, selected Page IDs and private candidates | Private settings source |
| Sanitized methods and reusable examples | Public teaching source |
| Current project goals, differences, task status and acceptance evidence | Existing current-state document, approved tracking Page or task system |
| Credentials, device paths, granted roots and session state | Target device's approved storage |

Select projects from actual work, not a fixed list. An existing tracker can serve multiple projects with distinct identities; durable work needs a recoverable record, not a new document for every repository. Preserve repository identity, repository-relative paths, source/base revision and content hashes. Locate each checkout on the destination device; do not treat an absolute path as its identity. Retrieve the authorized published/private source, preview selected changes, merge conflicts and back up before application. Verify saved source, remote delivery, destination content and client loading separately. Offline or unpushed work remains explicitly pending, not silently overwritten by a newer snapshot.

## Private settings in an approved Page

When requested, save selected portable personal instructions/settings and restore guidance in the approved private Page, while retaining their version-controlled owner. Inspect the destination's access/audience and existing purpose first; reuse a matching Page or create an independently useful settings topic. Preserve unrelated attachments and human content.

Use repository identity, relative file paths, source/base revisions and content hashes for a downloadable snapshot or selected content mirror. Keep its selected scope and unpublished changes clear. Save source updates through the maintained source first, refresh affected authorized Page content, and compare uploaded bytes/readback. Never restore blindly from the Page preview or change sharing permissions as part of a content update.

Store credentials, login state, actual device paths, allowed roots and company material only in their approved storage. On the target computer, retrieve the selected source or verified snapshot, resolve local locations, preview/merge/back up and use existing installers. Cloud storage, destination application and client loading require separate evidence. Saving a Page does not establish continuous synchronization or authorize a new scheduler.

## Update shared state, without an execution log

For maintenance decisions, apply [collected-evidence conditions](component-authoring.md#reuse-collected-maintenance-evidence). The selected private profile or project guide resolves the research destination; portable guidance contains no personal Page IDs.

- Locate the selected record through project instructions or existing tracking configuration at the start of relevant work, including user-opened new conversations. Use stable project/task identity and the record's existing location or Page ID; see [context continuity](context-continuity.md#recover-durable-goals-in-a-new-conversation).
- Keep durable goals/decisions/acceptance distinct from observed state, differences and pending work. Update the same record when these or its owner/next action/evidence change. Existing acceptance and deferred decisions survive device or conversation changes; reuse the approved environment and format rather than requiring a shared Page for company material.
- Read current content and instruction blocks before writing. Use the platform's current revision/hash guards and reconcile the save receipt with readback. A conflict requires rereading and rebuilding only the rejected change, not replaying successful operations.
- Match research by topic, source and applicable version. Merge additional evidence into the current conclusion, retaining unresolved contradictions and meaningful provenance. No substantive difference means no write.
- Consolidate superseded, agent-generated summaries in place. Preserve original attachments, human edits, unresolved work and evidence needed for acceptance. Keep compact completion evidence linking to its original artifact; do not copy entire logs or source documents into each update.
- New pages require an independently useful topic/project, not a date, device or schedule run. Do not create daily archives, empty project pages, repeated error entries or another collector for the same purpose. The maintained working set grows with distinct useful work, not elapsed runs.
- Inspect actual schedule identity, destination, frequency and enabled state before changing it. A document-maintenance request does not authorize new schedules, installations, Git delivery or broader data access. Notify only for a meaningful change, completion, failure or required user action when that matches the user's notification preference.

## Optional Apple integration

Use native product entry points and existing compatible tools before adding an adapter. Keep personal destinations and category names in the private profile.

Apple's public [EventKit API](https://developer.apple.com/documentation/eventkit/ekeventstore) runs on a compatible Apple device. [remindctl](https://github.com/openclaw/remindctl) provides reminder operations; [ekctl](https://github.com/schappim/ekctl) also provides calendar operations. Check the selected release/help, permissions and exact native IDs on that device before applying changes. Store task-to-native-ID mappings privately and reject ambiguous matches. Calendar synchronization requires an explicit need to reserve time and confirmed start/end/timezone. Completing a reminder does not prove code tests or release acceptance.
