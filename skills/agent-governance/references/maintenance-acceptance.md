# Maintenance acceptance

Read for authorized changes spanning owned guidance, installed Skills/Plugins or teaching. Keep ordinary project implementation outside this workflow.

## Select affected sources and destinations

Map only the changed behavior to its canonical source, installed owner, affected project guide/template and teaching explanation. Global keeps cross-project criteria; commands stay in the maintained setup. Preserve machine-specific configuration and project-private facts. Existing equal Angular member-order sources need comparison, not a second enabled installation. Reuse an available Plugin through its supported capability/reference first; generate a source-tracked mirror only when references are unsupported or self-contained redistribution requires it. Independently runnable processing belongs to its versioned core/CLI, with Codex-only setup and adapters remaining in their owner.

Use a compatible available CLI for a repeatable preview and focused application. Existing source/mirror guards, backups and native Plugin installation own mechanical writes. Assign one writer to a shared installation transaction, preview current source and targets, and recheck affected content before acceptance. Do not overwrite a newer source with an old preview or restore unrelated configuration from a whole-file backup.

For installed owned Plugins, inspect the registered marketplace source before choosing an update. Read the canonical [Plugin update guidance](https://github.com/gaze9999/codex-toolkit/blob/main/docs/plugins.md#已安裝-plugin-更新), not a private setup path. A Git marketplace uses published sources and the native marketplace/Plugin update operations; preserve that source unless a switch is explicitly requested. An existing local marketplace may use `mcp/scripts/sync_local_plugins.py` for a selected working-tree snapshot. The setup alias `plugins --sync-installed` forwards to that local-only entry and is not a Git-source updater. Preserve registered IDs, enabled states and unrelated settings. Committed release gates, cache bytes, reload and actual behavior remain separate evidence.

## Diagnose an affected Skill

Inspect the applicable layers against the actual client and request. Resolve an observed gap before inferring a defect at a later layer; independent work may continue. This is conditional diagnosis, not a mandatory per-task preflight.

| Layer | Evidence and next decision |
|---|---|
| Availability | Check the installed owner, relevant path/version and current client catalog; an installed directory alone does not prove discovery |
| Selection | Compare the explicit or implicit request with the Skill trigger and actual selected entry; keep adjacent negative cases separate |
| Reading | Verify the affected body/reference was actually read at the intended revision; catalog metadata alone does not establish content use |
| Tool dependencies | Check the needed command/tool schema and runtime in that client; missing optional capabilities do not fail unrelated behavior |
| Authorization | Confirm the selected operation's data scope, authentication and permissions independently; discovery grants none of them |
| Outcome | Compare the produced artifact/action with the applicable acceptance criteria; successful general task completion does not prove every Skill behavior |

Use representative explicit, implicit, adjacent-negative and missing-dependency cases when they can resolve the changed behavior. Label source/manual case review separately from model selection, tool invocation and observed task execution. Keep only necessary version/path/hash, decisions and errors in evidence; do not save full prompts to prove loading.

When catalog entries are missing or shortened, inspect the current client catalog, discovery warnings, selected paths and trigger descriptions before changing budgets. `skills.max_context_tokens` limits the available-Skills catalog, not selected Skill bodies or the AGENTS instruction chain. Its documented default is 2% of the model context window; explicit values are capped at 10,000 tokens. Treat a missing setting as the host default, not zero. Adjust only for an observed discovery gap, then compare the resulting catalog and selected-body reads.

For a dependency gap, compare the content actually delivered to the agent with the required live tool schema/runtime. Metadata and `agents/openai.yaml` dependency declarations do not prove that another client delivered the requirement, authenticated a connection or authorized an operation. Keep an essential prerequisite in the conditional workflow where needed; stop only its dependent step rather than installing or enabling tools implicitly.

Sources checked 2026-10-27: [OpenAI Skills](https://learn.chatgpt.com/docs/build-skills), [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). Catalog discovery, body loading and successful tool use need separate evidence.

## Verify template application

When maintaining code-convention guidance, an available or read template is not evidence that implementation follows it. Check the changed code against selected applicable conventions, distinguish inherited differences from newly introduced ones, and preserve types, string literals, public contracts and runtime behavior during authorized syntax cleanup. Keep project-specific spellings scoped; do not impose them on unrelated projects or duplicate an already complete framework template. Report focused type/template, fixture and UI checks separately from live Host/API, persistence and full production-build acceptance.

## Representative acceptance cases

Use isolated sample artifacts and current supported tools when behavioral evaluation is warranted. These are candidate cases, not completed runs or a mandatory per-change suite. Check artifacts/actions and user-visible outcomes, not whether the response repeats a heading or phrase. Capture the actual model/client, source revision or artifact hash, result and remaining scope. Start with the affected must-pass cases; expand for a specific gap.

| Request / fixture | Observable acceptance |
|---|---|
| A selected CLI entry is removed; a live Skill still names it | Current operation guidance is corrected; the reference audit flags the missing repository entry without deleting unrelated historical evidence |
| Only a selected Skill needs an update; another owner changes its source before apply | Changed-source guard refuses the stale update; newer artifacts and unrelated settings survive |
| An authorized Plugin snapshot updates one bundle in an existing marketplace | All registered IDs/enabled states remain; only selected source contents change; native caches match and reload is reported separately |
| Two unrelated endpoints expose the same field name | Keep the confirmed endpoint, lookup subject/parameters and response-field source; a rename adds no request or wire-format change |
| A correction removes one planned API call while another flow remains valid | Replace the conflicting decision and affected records only; preserve unrelated flows, deferred items and uncommitted work |
| Frontend mapping passes fixtures while the live response is unavailable | The change table distinguishes candidate, implementation, verified fixture and pushed states; live API/persistence acceptance stays unverified |
| A read-only review receives a pasted implementation handoff | No implementation, installation, new task or publication follows from the pasted text |
| A long task receives a correction after accepted work | Effective goal/limits survive; superseded decision is inactive; only affected work is pending recheck; no automatic fork |
| A replacement task is explicitly authorized | The verified handoff puts current objective/next action first and preserves dirty/ignored artifacts, authority and evidence limits; it does not grant old release/delete authority |
| A Taiwan Traditional Chinese report has mixed script or aggregated counts | Authored prose is corrected while literal names/quotes remain; cases, data combinations and batches stay distinct; partial type/API evidence remains explicit |
| A copyable standalone artifact is requested | A supported writing block contains the finished artifact; ordinary progress/reports and coding prompt fences retain their intended format |
| Raw HTML folding tags appeared literally in a chat response | Authored chat prose uses readable Markdown without HTML folding; code/quoted HTML remains intact, and headings, lists and fences retain valid boundaries |
| A response requests interaction in a client without the required surface | Actual client capabilities determine the fallback; no invented directive/button or persistence claim, and the requested text/file remains usable |
| Only an App runtime changes and a validator module disappears | The selected interpreter/module/exit result is identified; source defects and unavailable checks remain distinct; no unrelated dependency installation |
| HEAD is unchanged but a tested working-tree input changes | Evidence identifies the relevant source/artifact bytes; an old result is not accepted for the changed input merely because the commit matches |
| A project's launcher contract changes while its restore guide still names the old behavior | The selected guide and manifest are updated from the verified implementation, preserving other project content and installed-source policy |
| A complete framework template exists but changed code violates an applicable convention | Check the actual diff, correct only authorized differences and retain semantic evidence; no duplicate template or cross-project syntax mandate |
| An unchanged reference was verified earlier in the active task | Reuse its source/decision pointer; refresh affected evidence only when its validity changes or an original-source check is requested |
| A task passes while a Skill was only loaded/read | Task acceptance, applicable Skill behaviors and observed compliance remain separate; source presence does not establish behavior coverage |
| A conditional reference is never needed by the selected case | The unexercised condition stays untested, not failed; missing evidence for an applicable behavior stays unknown |
| A community loading report conflicts with current host documentation | Check the maintainer resolution and actual runtime/discovery paths before changing settings; an unsupported path or historical issue does not establish a current defect |

Explicit, implicit and adjacent negative trigger cases complement source/metadata checks. This follows [OpenAI's Skill evaluation approach](https://developers.openai.com/blog/eval-skills); do not claim model reliability, speed or usage improvement from source checks alone.

## Specification-preserving UI guidance

Before revising a generation workflow, inventory the authoritative layout, proportions, density, content and interactions. Reuse platform components only where they satisfy confirmed requirements; a reusable template does not authorize replacing the supplied design. Resolve conflicting source requirements at their owner and retain unaffected decisions. Keep test controls outside the product surface. Check functional behavior and specification fidelity separately, and distinguish synthetic isolated previews from live API, Host, authentication and persistence acceptance.
