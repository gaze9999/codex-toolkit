# Response presentation across clients

Read when maintaining cross-client response rules, finished-writing delivery or interactive presentation choices. Routine answers use applicable user/client instructions without loading this guide. Keep the short durable preference in Global or the target account/GPT instructions, and exact rendering/tool syntax in current client instructions and the owning Skill.

## Resolve the actual surface

Use the current Chat, Work, Codex Desktop, CLI, IDE or API context, available tools and supplied output schema. A model name, installed Plugin or Markdown file does not establish rendering support. Prefer ordinary readable Markdown when capabilities are unknown. Honor an explicitly requested plain-text, code, file or schema output.

Official behavior reviewed 2026-10-10:

- [Intelligent UI](https://help.openai.com/en/articles/20001598-intelligent-ui-in-chatgpt) composes text, graphics, buttons, forms and interaction in supported Chat. It is unavailable in Work, Voice and the GPT-6 Pro/Astra reasoning option. Preferences in Custom Instructions guide layout; check the actual account and interface before using it.
- [Visualizations](https://learn.chatgpt.com/docs/visualizations) is a separate supported Chat/Work entry, with desktop/mobile availability depending on rollout. The CLI and IDE do not render this visualization surface. A current Desktop session may supply additional rendering instructions and tools; use those actual capabilities.
- [Plugin UI](https://developers.openai.com/plugins/concepts/ui-guidelines) uses widgets supplied by a connected app/tool. Its cards, fullscreen or other modes are app integration surfaces; arbitrary reply HTML does not create them.

Recheck these product-specific facts when availability or rendering behavior changes. Do not change models, install Plugins, connect accounts or modify personalization merely to change a reply's layout.

## Choose the smallest useful format

| Intended use | Format and acceptance |
|---|---|
| Explanation, progress, plan or task report | Markdown paragraphs/lists. Put the result and material evidence directly in view. |
| Compare candidates with common fields | A normal Markdown table. Keep headings and numeric units clear. |
| Static labeled relationships or process | Mermaid when the client renders it; otherwise text or a requested portable diagram. |
| Explore parameters, filtering, time or spatial changes | An available interactive visualization tool. Read its current Skill/schema and verify the primary interaction. |
| Reusable finished message or document | A supported native writing block, or one complete copyable artifact when unavailable. Keep explanatory text outside it. |
| Code or a coding-agent prompt | The requested language fence; keep a coding prompt in one uninterrupted `text` fence, with model advice outside. |
| Missing material input or an actionable next step | A real native question/action entry if available and appropriate. A presentation-only button does not authorize an external write. |
| Download, editing, reproducible figures or durable application use | The requested usable file or application artifact, with a concise link or preview as supported. |

Small edits and simple facts normally need text only. Prefer standard plotting tools for scientific or exportable figures. Interactive previews do not replace a requested file, persistence, live-source synchronization or authorized publication.

## Preserve readable, real output

- In authored chat prose, use Markdown rather than raw HTML layout or folding tags such as `details`/`summary`. Preserve actual source code and quotations in their appropriate form. Keep required blank lines, complete fences and readable table boundaries.
- Use only native directives, writing variants, attributes and paths supplied by the current client. Do not invent renderer syntax, buttons, checked items, expandable panels or saved state. Keep required source citations and annotations in their supported format.
- Writing blocks contain completed reusable writing, not explanations, plans, progress, code or ordinary reports. An email block uses the current email schema and verified recipient fields when available. The current client defines block IDs, revisions and closing fences; avoid copying another client's syntax as a universal rule.
- Use native questions for genuinely missing decisions, with the tool's actual optional/required behavior. Use supported follow-up actions only for concrete relevant work. Do not add forms, selections or buttons that merely duplicate an already answered request.
- Keep key conclusions, values, units, source links and necessary limitations directly readable. Controls must have clear labels and keyboard operation; essential content cannot require hover. Distinguish source data, calculation and illustration, and verify labels, formulas and primary interactions.
- Treat preview state and connected/live data as separate capabilities. Do not imply a control saves across chats, writes to an account or follows a source continuously without actual support and authorized execution. Keep unapproved private data out of external queries and shared artifacts.
- Follow the client's link/media conventions, such as absolute workspace file links when required. A declared path or successful file write does not prove rendering. If formatting fails, supply readable Markdown, a simple table or the requested usable artifact rather than repeating unsupported markup.

## Check the changed guidance

Review an ordinary report, a requested copyable artifact, a comparison and an unsupported-interaction case. Confirm correct format choice, visible evidence, valid boundaries, preserved authorization and usable fallback. Source/link/package checks validate the instructions and distribution; actual rendering or interaction needs evidence in the selected client. Do not claim all active chats reloaded after synchronizing Global.
