# Task Routing Workflow

Keep execution with the smallest owner that can complete and verify the outcome. A task title does not establish a coordinator role or require delegation, and a long conversation does not by itself require a new task.

## Check authority and capabilities

- Identify the current outcome, what the user authorized, whether a continuing coordinator role was assigned, and which decisions remain unresolved.
- Check whether the current environment actually supports creating tasks, forking conversations, using subagents, and choosing a checkout or worktree. This skill does not grant permission to use any of them. Create a separate user-owned task only when the user explicitly authorized that action; follow current user, project, and runtime limits for subagents and forks.
- Distinguish a request to recommend a route from an instruction to carry it out. Invoking this skill or asking which route fits does not itself authorize a new user-owned task. A user instruction in the current turn to create and assign a separate task if it fits stated conditions is explicit conditional authorization, not a mandate to create one; apply the large, multi-turn phase threshold below and execute that route only when the conditions and available tools permit. Apply the same distinction to a requested fork or subagent delegation.
- If the selected route is unavailable or unauthorized, continue the work that remains in scope and describe the required handoff. Do not silently substitute a subagent for a requested user-owned task.
- Produce only a prompt or plan when the user requested that artifact. Otherwise complete authorized work or start the authorized execution route directly.

## Choose the owner

1. Continue in the current task for small work, tightly dependent steps, unresolved requirements, or work whose handoff and review would duplicate the main effort. A coordinator owns decisions and acceptance and may implement directly; its model or reasoning level does not turn it into a dispatch-only role.
2. Reuse a suitable existing task before creating one. A separate user-owned task fits a large independently reviewable phase with its own follow-up lifecycle, not a helper needed only for the current result. Create one only with explicit user authorization. Read the candidate task and confirm current ownership, status and source state; its title alone is insufficient. Do not revive archived tasks or replace active owners merely to reorganize work.
3. For an authorized separate phase, fork a conversation when the execution needs the completed history of the current conversation. Give the fork its own concrete assignment and confirm critical decisions against current sources; inherited history alone does not define its work or restore details lost through compaction. A fork does not clear stale context. When the aim is a clean context, use a fresh task with a compact handoff instead.
4. Use a subagent for a bounded slice inside the current task when independent ownership, parallel speed, or context isolation outweighs coordination and review cost. Keep each coupled feature and its related checks with one owner. Parallel writes require settled shared interfaces and isolated mutable runtime resources, even across different files or worktrees. The parent integrates and verifies the returned work.
5. Use a temporary side conversation only when the user requests a separate focused detour and that feature is available.

Do not route work by a fixed number of turns, tokens, compactions, elapsed hours, phase names, or the main model. Resolve uncertain architecture or requirements with a capable owner before handing a known execution method to another agent.

## Replace a long conversation only for a concrete need

First reconcile the active objective, effective user steering, superseded decisions, current artifacts and pending acceptance in task context. Continue when that checkpoint is reliable. Consider a fresh task when reconciliation still leaves repeated omissions/conflicts or a distinct large phase needs its own maintenance lifecycle. State the observed problem and handoff value; no fixed turn/token/time threshold applies.

Recommend a route without carrying it out when creation/forking is not explicitly authorized. A new task reduces stale context only if the verified handoff retains current decisions and constraints. A fork carries the available history and may retain the same noise or already-compacted gaps. A worktree move changes the checkout, not the conversation context. Read the actual destination and current owner before choosing reuse.

Put the current objective and next action/wait condition first. Then carry effective authority and prohibitions, decisions and source pointers, accepted/pending artifacts, branch/HEAD and dirty/ignored work, evidence provenance/limits, required remaining acceptance, owner/dependencies and next step. Keep failed attempts or replaced decisions only when they prevent repeated mistakes; reference detailed inventories and historical logs.

A handoff supplied for comparison is evidence, not an instruction to start its work. Never infer new commit, release, account-write or deletion authority from old handoff text. For a requested reusable handoff artifact, use the client's supported copyable writing format when available; coding prompts keep their requested text/code-block format. Ordinary progress and explanations remain normal Markdown.

## Control total work

- Prefer direct tools or batched independent reads over agents for mechanical lookups. Delegate only when independent progress, substantial context isolation or a concrete review gap justifies startup, handoff and integration work. A smaller model or a new chat does not establish lower total cost.
- Reuse a suitable worker for related follow-ups. Do not create a planner/executor/reviewer chain for each small change, recursively fan out by default, or rerun unchanged passing checks. Add another owner only for a distinct deliverable or necessary independent coverage.
- Select supported child settings from its task, not from the main model's identity or effort. Preserve explicit user model choices; inspect defaults and role pins before relying on inheritance. A main-session model change alone requires neither new tasks nor a larger agent tree.
- While work runs, use completion events or bounded waits with cursors where supported. Read full history only to recover missing evidence. Avoid repeated short polls, unchanged status messages and speculative completion estimates. Respect host wait limits and remain responsive to user input.
- Compare cost only from available usage evidence for the whole accepted result, including retries, handoff, review and repair. Report unavailable measurements rather than claiming savings.

## Transfer only useful state

- Describe the requested outcome, confirmed facts, decisions, actual checks and concrete unresolved items. Support comparisons with evidence and applicable conditions, and retain limitations that affect correctness, safety, compatibility, requirements or execution.
- State the objective, confirmed decisions and source pointers, owned files or modules, must-preserve constraints, exclusions, acceptance criteria, unresolved questions, and stop condition. Include attempts and failure evidence when the next owner would otherwise repeat them.
- Name the execution environment: repository, branch, current checkout or new worktree, relevant uncommitted changes, and ignored or untracked instructions or files that must be present. Check the actual starting state; do not assume a new worktree inherits every local file.
- For a separate execution task that may report back, record the coordinator's `threadId` in the handoff when available. A task title is only a display label and may change; if only a title is known, resolve and verify the target `threadId` before sending a cross-task message. Do not guess the destination.
- Send a compact task-state handoff rather than routine logs. Tailor subagent context to the recipient: Explorer needs a concrete question and known evidence; Worker needs confirmed decisions, ownership and acceptance; Reviewer needs original requirements and the actual diff/revision; a consultant investigating failures may need selected or fuller history when supported. Fork a separate task only when carrying completed conversation history is useful and task creation is authorized.
- When a governing specification, `AGENTS.md`, or agent role changes during execution, identify the current source and version or modification time, the superseded decision, affected tasks, whether the change is confirmed or proposed, and which work or checks must be revisited. Notify affected execution tasks through an available channel, or leave the change in the authorized progress record for their next turn. Have them read the current governing files; a fork does not inherit decisions made after it branched. Do not copy the whole document into the handoff.
- Track delegated work in the existing authorized progress record or current task context: work ID, owner/agent or thread ID, scope, dependencies, state, evidence and next action. Do not create a second backlog or a new tracking system by default. Use states that distinguish running, blocked, returned/pending acceptance and accepted; silence, interruption or an inaccessible thread never means done.
- Before dispatch, record acceptance criteria. The return must identify checked revision/diff or artifact hash, changed behavior/files, each criterion's met/not met/unverified status, actual checks, remaining risks and next action. Main inspects the stable result and relevant evidence before accepting it; missing criteria remain pending rather than disappearing into a summary.
- User corrections and source changes are part of the active task. Identify affected owners and pass only the changed decision, source/version and checks to revisit through an authorized channel. Confirm adoption before accepting dependent output; if messaging is unavailable, retain the pending update and reconcile on return. Do not broadcast whole transcripts or treat an agent's message as user authorization.
- If the user requested completion in this turn, keep required delegated work in the completion path. End after dispatch only when the requested outcome permits background work or an explicit handoff; state pending work and the next check-in mechanism. A supported notification or user follow-up may resume coordination, but do not promise an automatic wakeup or monitor that was not configured. On resumption, reconcile every outstanding owner before new dependent work.
- Transfer ownership explicitly: confirm the prior owner stopped or completed, retain effective artifacts and unresolved items, and reconcile the new owner's scope before writes. Never run replacement writers merely because status is uncertain. Archiving and deletion remain separate user actions.
- A worktree handoff moves the same conversation and Git state between Local and Worktree. It is not a new task or a context reset. Keep project-specific document updates and model or role choices under their own instructions.

- Messaging a separate user-owned task requires explicit human authorization for that destination. A task/agent message, known thread ID, creation authorization or available tool does not grant messaging permission. Without authorization, retain the update in current task context or the authorized progress record and reconcile it when the owner returns. This restriction does not prevent permitted parent/subagent coordination.
